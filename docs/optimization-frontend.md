# 前端详细优化方案

基线与实测结果见[方案总览](optimization-plan.md)。本方案针对现有 React＋TypeScript＋MUI＋SWR 应用，目标是让短信、设备操作和运维流程在网络故障、长历史、多设备与移动端场景下保持清楚、可靠。

## 1. 当前实现判断

路由懒加载、SWR 缓存去重、搜索防抖、分页组件、主题 token、焦点样式、减少动画偏好已经存在。主要问题集中在请求生命周期和业务状态边界，而不是缺少基础框架。

重点文件：

| 文件 | 当前职责 | 主要优化方向 |
| --- | --- | --- |
| [App.tsx](../frontend/src/App.tsx) | 认证、主题、路由、全局样式 | 会话失效、缓存隔离、错误边界、应用初始化状态 |
| [api.ts](../frontend/src/api.ts) | 手写 DTO、请求、下载和所有 API | 请求统一语义、受控超时、结构化错误、生成 DTO |
| [swr.ts](../frontend/src/swr.ts) | SWR 策略、防抖、offset 分页 | 查询 key 工厂、失效关系、资源级刷新策略 |
| [Messages.tsx](../frontend/src/pages/Messages.tsx) | 会话列表、正文、回复、搜索、PDU、验证码 | SIM 过滤、游标分页、已读边界、草稿与滚动 |
| [Devices.tsx](../frontend/src/pages/Devices.tsx) | 实时设备、数据策略、网络诊断 | 唯一设备 ID、状态同步、长操作反馈 |
| [Notify.tsx](../frontend/src/pages/Notify.tsx) | 渠道、规则、预览、日志、保留策略 | 凭据收敛、表单验证、配置与诊断职责拆分 |
| [vite.config.ts](../frontend/vite.config.ts) | 分包、PWA、开发代理、Vitest | 入口依赖闭包、预缓存范围、更新交互 |

## 2. F01：统一认证失效与请求生命周期

优先级：P1，建议与第一批正确性修复一起交付。

### 现状与证据

- `api.ts:32` 的 `request()` 在非成功响应时抛出 `ApiError`，没有统一认证事件。
- `App.tsx:83` 监听 `unhandledrejection`；SWR 读取通过 `onError` 处理 401。但 Messages、Devices、Backup 等写操作均有局部 `catch`，被捕获的 401 不会成为未处理 rejection。
- `App.tsx:92` 的 logout 忽略退出请求失败，然后刷新认证状态；网络故障时，用户不能明确判断退出是否完成。
- SWR 使用默认缓存，没有按登录会话显式隔离，也没有登出时统一清理敏感资源。
- 请求没有默认超时；`downloadFile()` 使用另一套 fetch 和错误解析。简单设置统一短超时会误伤当前最长 210 秒的运营商操作。

### 方案

1. 请求层在识别到业务 API 的 401 时，先通知认证状态容器，再抛错给调用方。登录失败的 401 仍由登录表单展示，避免误清理当前输入或产生循环刷新。
2. 将认证状态明确为 `initializing / authenticated / anonymous / unavailable`。认证状态接口无法连接时显示“无法连接服务”和重试入口，不把网络错误直接解释成密码失效。
3. 登录会话建立新的业务缓存 provider；退出或认证失效时卸载其子树、清除缓存和内存草稿。认证状态查询放在业务缓存作用域之外。
4. 退出请求失败仍立即隐藏本地敏感内容，说明服务器会话尚未确认撤销，并允许重试。不能把本地清屏描述为服务端会话已经失效。
5. 请求接口接受 `signal`、按操作配置的 timeout、请求关联 ID；合并外部取消信号与超时信号。为读取、写入、上传分别确定预算；长硬件操作迁移到 B06 作业 API 后，提交请求使用短超时。
6. 错误类型区分网络错误、超时、取消、认证失败、校验失败、设备离线、硬件错误和未知执行结果。保留 `+CMS` 等诊断信息，提供中文摘要。
7. 统一 JSON、上传、下载的状态码解析。只允许读取按策略重试；短信、呼叫、AT、恢复不做透明重试。

### 验收

- 服务端撤销会话后，发送短信、保存渠道、下载备份任一请求收到 401，页面立即进入登录状态，即使调用方捕获异常也生效。
- 用户重新登录后看不到上一会话缓存的短信、渠道 secret 和诊断结果。
- 网络断开、读取超时、主动取消、密码错误呈现不同反馈；不出现无限转圈。
- 取消浏览器请求时，不把已经提交的硬件操作显示为“已取消执行”。

## 3. F02：补齐读取错误、页面错误与陈旧状态

优先级：P1。

### 现状与证据

`Dashboard.tsx:85`、`Devices.tsx:178`、`Sims.tsx:131`、`Tasks.tsx:149`、`Operations.tsx:177`、`Logs.tsx:68` 主要依据 `!data` 返回 `<Loading />`，没有消费读取错误。部分辅助资源默认 `[]` 或 `{}`，失败可能呈现为“没有记录”。`Suspense` 覆盖异步加载等待，但未提供路由级渲染或 chunk 加载错误恢复。

### 方案

建立轻量 `QueryState` 和 `PageErrorBoundary`，复用 MUI，不引入新的状态框架：

| 状态 | 用户看到的内容 | 行为 |
| --- | --- | --- |
| 首次加载 | 保留页面标题、布局骨架和可用导航 | 避免整屏长期空白 |
| 首次读取失败 | 错误摘要＋重试按钮 | 显示网络或权限原因，不伪装空列表 |
| 成功但空数据 | 业务解释＋适当入口 | 如“暂无会话”“尚未发现模块” |
| 已有数据刷新失败 | 继续显示数据＋更新时间＋“刷新失败” | 用户知道数据可能过时 |
| 参数切换中 | 保留旧结果但显示正在加载的新条件 | 防止旧范围数据被误认作新结果 |
| chunk 或渲染错误 | 当前页恢复面板 | 保留导航；按需提供重新加载 |

错误边界仅负责渲染失败；异步请求和事件处理仍由请求层与页面处理。对 429 尊重 `Retry-After`，不把配置错误等永久失败当作短暂故障反复请求。

验收：分别模拟主资源和辅助资源 500/503、离线、chunk 加载失败，页面可解释、可重试、可导航；刷新失败不重置正在编辑的内容。

## 4. F03：短信会话正确性、历史访问与已读语义

优先级：null SIM 隔离为 P0；分页、已读及滚动为 P1。依赖 B03 的明确过滤契约和 B02 的唯一设备身份。

### 4.1 三种 SIM 查询语义

`Messages.tsx:475` 使用 `sim_id: thread.sim_id ?? undefined`，API 在省略 `sim_id` 时查询全部卡。无 SIM 会话因此会混入其他卡同 peer 的短信，而标记已读使用的是 `sim_id IS NULL`，读取与写入范围不一致。

采用显式过滤结构，类型层面区分 `all`、`assigned(id)`、`unassigned`，网络层映射到 B03 的参数。不把 `null` 自动转换为“省略过滤”。无 SIM 的会话是否继续按设备拆分，须在协议设计时确定；即使沿用当前会话模型，也必须先实现无 SIM 与其他卡隔离。

验收数据：同一 peer 下至少两张真实 SIM 和一个 unassigned 会话；列表、正文、总数、已读、搜索、导出使用相同范围。

### 4.2 固定页大小的双向增量读取

当前 `THREAD_PAGE=200`，点击“加载更早”执行 `reach += 200`，每 5 秒重新读取整个扩大后的窗口；后端 `limit<=2000`，再点一次请求 2,200 即 422。会话列表默认只取 200 个，缺少继续加载；本地搜索只能匹配这些会话，但另有全量短信搜索弹窗，应保留二者区别。

方案分两步：

1. 紧急修复阶段，使前端遵守后端上限，达到上限提供清楚提示及搜索/导出入口，消除 422 死路。该补丁只是过渡，不算完成长历史访问。
2. 为正文提供 `(ts,id)` 历史游标，每页 100–200 条；前端使用分页缓存保存历史，仅刷新尾部新增消息和可见消息的回执状态。合并按消息 ID 去重，历史游标与回执更新版本分开。
3. 会话列表支持分页及服务端筛选；在新消息导致排序变化时，客户端合并去重并维护选中会话。不把动态会话排序当成永不变化的静态分页。
4. 用户一次访问 10,000 条时，按测量决定是否使用窗口化列表。先做稳定分页与缓存，再验证 DOM 数量、可变高度、代码复制和键盘访问。
5. 普通列表 DTO 不携带 `raw_pdu` 等诊断大字段，展开消息诊断时再加载详情。兼顾损坏短信的 `truncated/recovered_body/recovered_code` 展示。

### 4.3 已读与滚动

当前 SWR fetcher 读取后调用 `markRead()`；后端将整个会话未读记录置已读。读取与标记之间到达的新短信也可能被标记，数据筛选还可能标记当前不可见类别。应把已读从 fetcher 副作用拆出，仅在会话可见且页面处于前台时推进已读水位或提交实际可见 ID。

明确产品语义：默认以用户打开并看到的范围推进已读，不因预取历史、后台 revalidation 或失败请求改变已读。若选择“打开会话即全部已读”，也必须限定到当前已知水位，避免误标刚到达的数据。

当前 `newestId` 变化会调用 `scrollIntoView()`，无论用户是否正在翻阅历史。改为仅在接近底部或本人发送时跟随；阅读旧消息时显示“有 N 条新消息”。加载旧页前后保持首个可见消息及其偏移。

### 4.4 草稿与定位

会话组件因 key 改变而重挂载，草稿会清空。采用会话级内存草稿，切换后可以恢复；登出时清除。默认不把短信正文放进 localStorage；是否跨刷新保存属于单独产品决策。

把当前会话、列表筛选和日志页码纳入路由状态。手机号与 SIM 标识属于敏感数据，不默认写入可分享 URL；可优先使用服务端不透明 conversation ID，部署访问日志也避免记录敏感 query。浏览器返回应关闭会话或还原筛选，而不是直接离开整个短信流程。

### 验收

- 持续插入新短信期间，浏览 10,000 条历史无缺页、无重复、无 422。
- 不会因打开无 SIM 会话显示其他卡短信；已读数与列表一致。
- 阅读历史时新消息不抢滚动位置；发送后可回到自己消息。
- 切换会话保留未发送草稿，登出后清除；搜索命中旧会话仍可定位。

## 5. F04：统一实时状态与缓存失效

优先级：P1。

### 现状与证据

- `Devices.tsx:76` 的 `/api/devices` 没有 refreshInterval，但同页历史每 15 秒刷新。后台上报后设备卡可能滞后，历史图却已更新。
- 当前 key 有字符串和元组两类。例如短信会话 key 为 `['/api/messages/conversations', content]`，实际 URL 是 `/api/conversations`；这是合法的 SWR 用法，但不符合文件注释中“key 就是 API 路径”的简单约定。
- 页面分别轮询 5、10、15、30 秒，同类日志有不同 key 表达。日志页多个面板的 hooks 持续挂载，标签切换不一定停止不可见资源请求。
- 不应假设 SWR 会持续轮询隐藏标签页：其默认隐藏/离线行为应结合仓库锁定版本确认，问题重点是当前仍挂载的非活动业务面板。

### 方案

1. 建立 `queryKeys` 工厂，包含资源、排序后的过滤参数、分页和身份；建立 domain hooks，页面不自行拼接 key。
2. 将失效规则集中到成功 mutation，保留精确资源更新，不每次全站 `mutate()`。
3. 设备当前状态使用 10–15 秒刷新；趋势可 60–120 秒，长历史 1–5 分钟；短信会话尾部 5 秒，渠道规则按事件失效和 focus 刷新。上述周期是起始预算，按请求数量和业务需求调整。
4. 非活动日志页签以 `null` key 暂停查询；重点避免预览或编辑表单被 revalidation 重置。
5. 暂保留轮询。仅当实测刷新延迟或请求量不满足预算时，再添加独立浏览器 SSE 失效通知；SSE 只传资源 ID/版本，不复用 Agent `/ws`，失效通知丢失时仍可通过重新读取恢复。

| 写操作 | 应失效/更新的资源 |
| --- | --- |
| 修改 SIM | SIM 列表、设备展示、overview、相关会话摘要、SIM 运维事件 |
| 标记已读 | 当前会话、会话摘要、导航未读数 |
| 短信发送/回执 | 当前会话、会话列表、overview、发送作业状态 |
| 修改射频/数据策略 | 目标设备、overview；历史等待实际状态上报或显式刷新 |
| 修改通知渠道 | 渠道、带渠道名称的规则、必要的投递状态 |
| 修改任务 | 任务列表、任务同步版本、overview 计数；实际运行后更新日志 |
| 确认事件 | 对应事件列表、overview 告警摘要、导航计数 |
| 恢复数据库 | 整个业务缓存作用域和认证状态 |

验收：各主要页面记录 1 分钟请求数；非活动页签无周期请求；设备卡和详情最终显示同一设备 ID 对应的新状态；跨页标签与计数在一次刷新预算内收敛。

## 6. F05：入口体积、图表与 PWA 更新

优先级：P1。当前已有懒加载和 manualChunks，优化目标是实际依赖关系。

### 方案

1. 分析构建模块图，定位 charts 为什么进入入口预加载闭包；现阶段只确认产物存在预加载，尚未确定具体共享模块归属原因。
2. 在保留路由懒加载的基础上调整 chunk 边界与共享 helper 归属；必要时把图表容器再延迟到可见区域。验证登录和短信页没有图表网络请求后，再决定是否细拆 vendor。
3. 首先复用当前 Recharts；不因单个 chunk 大就更换图表库。设备历史服务端已聚合约 360 点，应测量多设备合并、SVG 节点数量和 React 提交时间。
4. 明确 PWA 策略：入口及必要静态资源预缓存；大图表等资源按需缓存。检查 install 阶段资源请求，避免把后台预缓存误算成页面必需 JS。
5. 维持 API、短信正文、渠道凭据和备份不进入 Service Worker 缓存。当前配置未声明 API runtimeCaching，不应把此要求写成“修复已存在的 API 缓存泄露”。
6. 从自动更新策略演进为可解释的更新提示。用户有未发送草稿、恢复或硬件操作时，允许延迟刷新；提供版本信息和失败恢复入口。
7. HTML、SW 与带 hash 静态资源使用不同缓存策略，和 B10 协同；部署保留上一版必要资源或具备清楚的 chunk 加载恢复，减少页面开着时发布引发的错误。

### 验收

- 冷缓存进入登录页，charts 不在 modulepreload，也不作为登录必需资源请求；单独记录 PWA install 请求。
- 记录构建体积、解析执行时间和低端设备交互时间；入口 gzip JS 以总览预算为目标，不靠增大 chunk warning 阈值通过。
- 离线时显示连接不可用，不能显示伪造的“最新设备状态”。
- 新版发布时保留未发送草稿；选择更新后资源版本一致，不出现循环刷新。

## 7. F06：长操作、危险操作与结果未知

优先级：P1，与 B06 配套。

运营商扫描、选网和诊断最长等待 165–210 秒；当前主要通过局部 busy 状态管理。设备页 `busy` 以名称标识，身份修复后应按设备 ID 与操作类型隔离。

采用清楚的操作状态：`提交中 → 排队 → 执行中 → 成功 / 失败 / 结果未知`。后端返回 operation ID，页面显示经过时间和最后更新时间；关闭详情或刷新页面后可再次查看。真实执行状态来自服务端，不能用前端定时器假装进度百分比。

短信/呼叫超时提示“结果尚未确认，请先检查记录”，避免无条件重试；对于可安全重试的查询操作，提供重试入口。浏览器取消只表示停止等待，硬件是否取消由后端协议决定。

把 `window.confirm()` 收敛成可复用确认弹窗，明确目标 SIM/设备、影响和正在进行的操作；沿用已有 Backup 恢复确认结构。普通编辑不增加确认步骤。射频关闭、删除任务、恢复数据库分别使用适合其风险的文案与主按钮，不共用含糊的“确定”。

验收：并行操作两个设备不串 busy；操作未完成离开页面可找回；网络超时不自动重发短信；确认弹窗键盘可到达、Escape 和关闭后的焦点返回正确。

## 8. F07：逐页交互与响应式优化

优先级：P1/P2。以下是基于代码结构的设计方案，不代表已完成浏览器视觉审核。

| 页面 | 优化重点 | 交付与验收 |
| --- | --- | --- |
| Dashboard | overview、趋势、历史、事件独立失败；明确当前时间窗口和更新时间 | 任一辅助接口失败不清空整页；“今日”与 B12 时区口径一致；提供图表文本摘要 |
| Messages | 双栏/单栏切换、完整历史、草稿、回复目标 | 375 px 宽度和虚拟键盘下发送框可用；浏览器返回恢复列表；长号码正文不撑破页面 |
| Devices | 已有移动卡片继续保留；状态新鲜度、隐藏离线数量和详情一致性 | 展示 Agent 与设备唯一身份；离线设备开关有数量提示；长任务持续可见 |
| Sims | 标签、余额、阈值、期限表单的字段验证 | 金额和币种错误贴近字段；保存不覆盖另一处更新，必要时 B11 提供版本冲突反馈 |
| Tasks | 动作类型与必填字段联动；调度说明与同步状态 | 解释 interval 单位/cron 时区；显示下次执行和 Agent 是否应用配置；失败不丢输入 |
| Console | 保留明确目标和执行历史，区分 AT 返回与链路错误 | 设备离线时禁止发送；危险指令确认按既有能力边界设计；历史不默认存敏感正文到持久缓存 |
| Notify | 渠道、规则、测试器与最近投递分区；凭据不回填明文 | 窄屏下替代 `minWidth:560` 的规则宽表，或让主要操作无需横向寻找；字段错误定位；新建先验证渠道类型 |
| Operations | 健康、活动事件、审计独立读取 | 故障按严重程度和发生时间排序，确认与解决语义清楚；筛选和分页可恢复 |
| Logs | 当前页签按需读取；固定筛选快照或游标避免新日志推动页边界 | 查旧日志不自动跳页；搜索 debounce 后重置页码；结果为空与请求失败不同 |
| Backup | 文件大小、验证阶段、恢复前快照和恢复状态 | 上传前显示大小及上限；恢复过程不重复提交；失败可访问回退说明 |
| Settings | 密码、Token 轮换与配置状态 | 密钥默认隐藏且按需获取；轮换显示宽限期与 Agent 更新情况；复制结果反馈明确 |
| Login | 初始化、连接失败和密码失败三种状态 | 支持密码管理器和粘贴，错误与字段关联；认证不可达时有重试 |

可访问性验收沿用现有 focus-visible、图标标签和 reduced-motion，进一步检查弹窗标题关联、输入错误描述、更新状态播报、焦点回到触发按钮、缩放和对比度。MUI Dialog 的基础焦点能力无需自造，需测试组合后的实际行为。

移动端主要操作建议提供约 44×44 CSS px 触控区域，这是产品体验目标；不要误称为 WCAG 2.2 AA 的统一硬性要求。AA 的 Target Size (Minimum) 以 24×24 CSS px 为基准并允许规定的例外。[W3C 目标尺寸说明](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

测试视口建议为 375、768、1280、1920 px；320 px、200% 缩放及长中文/英文内容作为边界。数据表可以在局部容器横向滚动，但页面整体不得溢出，主要操作必须易于到达。

## 9. F08：DTO、查询接口与模块边界

优先级：P1/P2，随功能改动推进。

### 契约

`api.ts` 同时维护近 700 行客户端类型与端点；后端大量响应是 `dict[str, Any]`。先由 B11 定义稳定响应模型、分页、错误码和 device ID，再在 CI 离线导出 OpenAPI schema 并生成 DTO。生产可以继续禁用公共 `/openapi.json`，不需要为了生成类型暴露在线文档。

业务展示模型与网络 DTO 分开：例如布尔/未知三态、金额字符串、可恢复短信正文不能被自动转换丢失。边界字段采用可追踪的兼容转换，对关键响应可增加运行时形状验证，但不为所有数据重复维护两套完整 schema。

### 建议目录

以下路径为拟议结构，不是当前已有文件：

```text
src/
  app/                 认证、路由、主题、错误边界
  shared/api/          HTTP、错误、生成 DTO、查询 key
  shared/ui/           QueryState、确认弹窗、分页与通用状态
  features/messages/   列表、正文、搜索、草稿与领域 hooks
  features/devices/    状态、详情、网络操作与领域 hooks
  features/notify/     渠道表单、规则表单、预览与投递
  features/operations/ 事件、审计与诊断
```

拆分准则是独立职责、可单独测试和变化频率；不机械地把 JSX 切成大量只传 props 的小组件。优先拆 `ThreadView` 与短信数据 hook、`ChannelDialog` 与渠道字段 schema、设备网络操作与详情面板。主题和 token 保持一处定义，避免新旧目录同时维护两套样式规则。

验收：接口改字段会在生成/类型检查阶段报错；domain hooks 可单独测试过滤与失效；一次页面功能修改不要求同步编辑多个无关页面。

## 10. F09：大文件下载与上传反馈

优先级：P1/P2，依赖 B07/B10。

后端 CSV 已流式读取，前端 `downloadFile()` 却调用 `response.blob()`，必须完整接收再发起保存。对大备份会延迟可见反馈并占用浏览器资源；具体内存或磁盘落点由浏览器实现决定，不能直接把文件大小等同于 JS 堆增量。

优先采用同源浏览器原生下载，让浏览器承担保存和进度；另用短请求检查认证或创建下载作业。若产品必须展示应用内流式进度，则使用受支持能力并提供回退，避免为小规模部署引入复杂下载依赖。

恢复上传沿用原始文件请求或后续上传会话；客户端预检大小、文件扩展名只作体验辅助，服务端验证是最终边界。区分上传、数据库校验、恢复、重连阶段；失败显示是否已修改数据库和回退位置。取消上传清理临时资源，不能伪装为已撤销开始后的数据库恢复。

验收：大文件下载有及时可见反馈；服务器 401/413/空间不足有明确错误；取消与网络断开不残留无限 busy；敏感下载响应不被公共缓存。

## 11. F10：测试策略与分阶段验收

优先级：P1，随问题修复同步补充。

保留现有 101 项测试。新增测试优先覆盖用户可感知的边界，不以组件拆分数量或快照数量衡量质量。

| 层级 | 新增场景 | 工具/方式 |
| --- | --- | --- |
| 请求层 | 已捕获 401、超时、取消、结构化校验、下载错误 | 现有 Vitest 与可控 fetch mock |
| 查询 hooks | null SIM 参数、缓存 key 隔离、mutation 失效、未激活页签停止查询 | Vitest、SWR 测试 provider、受控时钟 |
| 页面交互 | 2,000 条边界到游标迁移、滚动新消息、草稿切换、表单错误、未知命令结果 | Testing Library，验证用户行为而非内部 state |
| 浏览器 | 登录→收信→打开会话→回复→登出；恢复校验；网络中断；PWA 更新 | 选定浏览器自动化工具后加入 CI，使用合成数据与 mock Agent |
| 可访问性 | 弹窗键盘流程、输入标签/错误、图标按钮、缩放 | 自动扫描＋人工键盘和读屏抽查 |
| 性能 | 登录依赖、SW 安装请求、长会话 DOM、多设备图表 | 构建报告＋实际浏览器 trace |

首批浏览器流程建议覆盖 Chromium 与移动视口；PWA、下载和 Safari 相关能力另行验证，不能用 jsdom 通过代替真实浏览器兼容性。

每批交付继续执行 `npm test`、`npm run lint`、`npm run build`。涉及契约同时跑 Server 测试；涉及 hardware operation 同时跑 Agent 协议测试。行为不变的组件搬迁只需相关回归，不新增重复实现逻辑的测试。
